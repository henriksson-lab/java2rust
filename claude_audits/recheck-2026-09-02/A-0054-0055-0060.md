### SURVIVING adjacent defect — `E0308` when a void method's LAST statement is a try/catch and the `Result` promotion originates in the catch body

Minimal repro (`U.java`, javac-clean, runs fine under Java):

```java
public class U {
    public void divInCatch(int b) {
        try { throw new RuntimeException("x"); }
        catch (RuntimeException e) { long a = 7; System.out.println(a / b); }
    }
    public void divInTry(int b) {                                   // control: OK
        try { long a = 7; System.out.println(a / b); }
        catch (RuntimeException e) { System.out.println("c"); }
    }
    public void divPlain(int b) { long a = 7; System.out.println(a / b); }   // control: OK
    public static void main(String[] x) { U u = new U(); u.divInCatch(2); u.divInTry(2); u.divPlain(2); }
}
```

```
$ javac -d . U.java && java -cp . U
3
3
3
$ $B U.java > U.rs 2>/dev/null ; grep -n "pub fn div_" U.rs
2037:    pub fn div_in_catch(&self, b: i32) -> Result<(), JavaException> {
2041:    pub fn div_in_try(&self, b: i32) {
2045:    pub fn div_plain(&self, b: i32) -> Result<(), JavaException> {
$ printf '\nfn main(){ U::main(Vec::new()); }\n' >> U.rs
$ rustc --edition 2021 -o U_bin U.rs
error[E0308]: mismatched types
    --> U.rs:2037:43
     |
2037 |     pub fn div_in_catch(&self, b: i32) -> Result<(), JavaException> {
     |            ------------                   ^^^^^^^^^^^^^^^^^^^^^^^^^ expected `Result<(), JavaException>`, found `()`
     |            |
     |            implicitly returns `()` as its body has no tail or `return` expression
error: aborting due to 1 previous error
```

The signature promotion is *correct* (the catch body's `a / b` lowers to a `?`), but the
emitted body has no tail `Ok(())`. `div_plain`, whose body is the same statements without
a `try`, does get `return Ok(());`.

Boundary of the case (`V.java`, all three compile and run correctly):
- promotion from a statement **before** the try, try/catch last → OK
- promotion from a **`finally`** body, try/finally last → OK
- promotion from a catch body but with **any statement after** the try → OK

So the trigger is specifically: unit-returning method, try-with-`catch` as the final
statement, `?` originating inside a catch arm.

Attribution: I could not run the pre-fix binary, so I cannot say this is a strict
regression. The mechanism is causally downstream of the 0060 fix (the promotion only
happens because the signature planner now *sees* the catch body); before the fix the same
input would have emitted a `?` in a `()`-returning function, which is also a compile error.
Either way it is live today on javac-clean mainstream Java.
