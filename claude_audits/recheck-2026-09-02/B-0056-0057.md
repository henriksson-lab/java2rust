# 0056 — `null` is planned away, not represented

## VERDICT: **PARTIALLY FIXED, WITH THREE REGRESSIONS**

The two headline silent-wrong-output claims are genuinely **FIXED**: reference
arrays now store `Option<T>`, and no probe produced a silent constant fold of a
null test. The fold is now *sound* rather than merely absent — for a nullable
field, a method returning `null`, and a `null` passed as an argument it lowers
correctly; where it cannot, it emits a loud `compile_error!`.

But **`Map.get` into a declared local has regressed hard**. It is now planned as a
borrowed non-optional carrier with an eager `.expect("Java null receiver")`, which
(a) makes every `x == null` on it a `compile_error!` and (b) makes a plain map
miss a **process abort where Java yields `null`**. This is the most common null
idiom in Java and it takes down the promoted `MapGetNull2.java` fixture plus the
`get`-or-create bucket pattern. Two more promoted fixtures (`LinkedNode.java`,
`NullableArrayLengthCatch.java`) fail on a doubled null-unwrap projection —
exactly the defect §5c's "seventh pass" records as fixed.

## B. Nullable array element loses nullability at a source-method return boundary

`scratchpad/probes/NullFold5.java`:

```java
static String[] table = new String[2];
static String get(int i) { return table[i]; }
public static String run() {
    table[0] = "z";
    String a = get(0);
    String b = get(1);
    return (a == null) + "," + (b == null) + "," + a + "," + b;
}
```

Java: `false,true,z,null`. Translation fails to compile with two
`unsupported Java null comparison` errors. The array storage is correctly
`Vec<Option<String>>`, but the getter throws the nullability away:

```rust
pub fn get(i: i32) -> String {
    return Self::__static_table()[i as usize].as_ref().expect("Java null receiver").clone();
}
```
