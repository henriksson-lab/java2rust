# Rust Slot Shape Refactor Audit

This file tracks how close the implementation is to the design locked in
`docs/rust-slot-shape-and-object-representation.md`.

Status legend:

- `Proved`: implemented with direct tests or guard scans.
- `Mostly`: implemented for the intended responsibility boundary, with known breadth gaps.
- `Partial`: scaffold exists, but important cases still need implementation.
- `Missing`: not implemented in a meaningful way yet.

## Current Estimate

The refactor is about 85-90% complete as an architectural refactor.

The important boundaries are now in place: Java typing, shape projection,
signature solving, representation policy, coercion, and rendering/lowering are
separate enough that new behavior can usually be placed in the right layer.

It is not complete as a semantic translator design yet. The remaining work is
mostly breadth: making the constraint solver and fallback matrix cover all
non-string types, storage/escape cases, open object hierarchies, boxed dyn
trait cases, and broader diagnostic surfacing.

## Closest Remaining Work

1. Expand the signature fixpoint so it can propagate public/unknown API,
   owned escaping polymorphism, and capability constraints across params,
   locals, fields, returns, and calls.
2. Complete the object fallback matrix: concrete struct, closed enum, dyn trait,
   boxed dyn trait, erased object, and unsupported diagnostic.
3. Make capability use systematic so rules are expressed as facts about types,
   not as Java type-specific branches.
4. Strengthen diagnostics for ambiguous ownership, unsafe casts, unsupported
   hierarchy mappings, and failed user overrides.
5. Run a final module-boundary audit over `lower.rs`, plan modules, shape modules,
   render modules, and coercion once the above gaps are closed.

## Completion Criteria

The refactor can be called complete when:

- every row above is `Proved` or intentionally documented as out of scope;
- adding a new Java feature has an obvious place for facts, shape constraints,
  representation policy, coercion, and rendering;
- no lowering path directly decides ownership, view, dispatch, or cast strategy;
- all fallback choices are explicit policies with diagnostics or runtime behavior;
- `cargo fmt`, `cargo test`, `cargo clippy`, and responsibility-boundary scans pass.
